Manual del Rol Super Admin

Sistema de Gestión de Transporte

Documento técnico interno con la arquitectura completa del proyecto, mapa de navegación del panel de administración, estructura de base de datos, servicios del dominio, API REST, reportes y procedimientos operativos para el equipo de desarrollo y administración del sistema.

Versión 1.0 · Junio 2026 Asamblea Legislativa Departamento de Transporte

1. Introducción

El rol Super Admin es el nivel más alto de acceso en el sistema. Tiene permisos totales sobre todos los recursos, páginas, reportes y operaciones del panel de administración Filament, así como acceso completo a la API REST. Este manual describe la arquitectura interna del proyecto, la estructura de navegación, los recursos disponibles y los procedimientos técnicos que un Super Admin debe conocer para administrar, mantener y depurar el sistema.

🔑 Alcance del Super Admin
✅ Acceso total al panel /admin — todas las páginas y recursos.
✅ CRUD completo en todos los catálogos, solicitudes y configuraciones.
✅ Gestión de usuarios y roles (Filament Shield).
✅ Acceso sin restricciones a la API REST (/api/*).
✅ Exportación de reportes PDF, Excel, CSV.
✅ Ejecución de comandos Artisan (migraciones, seeders, shield:generate).
✅ Visualización de auditoría y trazabilidad completa.
⚠️ Responsabilidad: El Super Admin puede modificar cualquier registro del sistema, incluyendo roles y permisos. Las operaciones de borrado no tienen restricción. Se recomienda extremar la precaución al eliminar registros o modificar la estructura de permisos de Shield.

3. Acceso al sistema

URL del panel de administración: https://[dominio]/admin

La autenticación se realiza mediante LDAP (Active Directory de la Asamblea). El formulario de login (app/Filament/Pages/Auth/Login.php) intenta autenticar contra LDAP primero; si falla, permite login local con credenciales almacenadas en la base de datos.

canAccessPanel() retorna true si el usuario tiene rol super_admin o superadmin. En entorno local (APP_ENV=local) retorna true para cualquier rol. Bloquea a motorista y solicitante.

5. Gestión de usuarios y roles

5.1 UserResource

app/Filament/Resources/UserResource.php — Gestión completa de usuarios del sistema.

Campos principales: name, username, email, password, activo, unidad_solicitante_id, departamental_id, roles (Filament Shield multi-select). Búsqueda global habilitada sobre name, username y email.

5.2 RoleResource (Shield)

app/Filament/Resources/RoleResource.php — Gestión de roles y permisos vía Filament Shield 3.

Cada rol puede tener permisos individuales para cada recurso: view_any, view, create, update, delete, delete_any, force_delete, restore, replicate, reorder.

Regenerar permisos: Ejecutar php artisan shield:generate --all para sincronizar todos los permisos con las políticas existentes. Es seguro — usa findOrCreate, nunca elimina permisos existentes.

13. Procedimientos operativos

13.1 Crear un nuevo usuario LDAP

  1. El usuario intenta iniciar sesión en /admin.
  2. El login LDAP lo autentica contra AD y lo crea automáticamente con rol solicitante (app/Filament/Pages/Auth/Login.php:156 y app/Http/Controllers/Api/TokenAuthController.php:107).
  3. Si necesita otro rol, el Super Admin debe ir a Administración → Usuarios, buscar al usuario, editarlo y asignarle el rol correspondiente.

13.2 Regenerar permisos de Shield

php artisan shield:generate --all
Escanea todas las políticas en app/Policies/ y crea los permisos faltantes usando findOrCreate. No elimina permisos existentes. Ejecutar después de crear un nuevo Resource o Policy.

13.3 Ejecutar migraciones y seeders

php artisan migrate — Ejecuta migraciones pendientes.

php artisan db:seed — Ejecuta todos los seeders (respetando orden en DatabaseSeeder.php).

php artisan migrate:fresh --seed — Borra todo y reconstruye desde cero (solo en local/desarrollo).

13.4 Asignar contratos (combustible vs mantenimiento)

Los contratos se dividen en dos tablas separadas:

  • Combustible → contrato_combustibles (9 contratos: solo gas/diesel). Gestión desde Catálogos Globales → Contratos de Combustible.
  • Mantenimiento → contratos_mantenimiento (29 contratos: mantenimiento, llantas, seguros, transporte). Gestión desde Catálogos Globales → Contratos de Mantenimiento.

13.5 Asignación Previa

  • Combustible: Desde Gestión Operativa → Revisión, vincular solicitud a un detalle de lote activo.
  • Mantenimiento: Desde Gestión Operativa → Revisión, vincular solicitud a un contrato activo con saldo disponible.

13.6 Contratos con número pendiente

4 contratos tienen placeholders (SIN-NUMERO-94, SIN-NUMERO-101, SIN-NUMERO-103, SIN-NUMERO-104) a la espera de los números reales del Departamento de Transporte.

13.7 Contratos con monto en 0

8 contratos de mantenimiento tenían monto nulo en los datos legacy. Se sembraron con monto = 0.00 y una nota en observaciones. Actualizar cuando se disponga de los montos reales.

14. Consejos prácticos

🛡️ Shield regeneration es seguro: Ejecute php artisan shield:generate --all sin miedo. Usa findOrCreate, nunca borra permisos. Es la forma correcta de sincronizar nuevas políticas.
🔍 Búsqueda global: Los recursos SolicitudTransporteResource, SolicitudCombustibleResource y SolicitudMantenimientoResource tienen búsqueda global habilitada. Busca por código, ticket, nombre de solicitante, placa, etc.
⚠️ Entorno local: En APP_ENV=local, canAccessPanel() retorna true para todos los roles. No asuma que los permisos de Filament Shield funcionan igual en producción.
📂 LDAP nuevos usuarios: Desde Junio 2026, los nuevos usuarios LDAP se crean con rol solicitante. Los usuarios LDAP existentes sin rol no se modifican. Si necesita cambiar el rol, hágalo manualmente desde UserResource.
🔗 Auditoría siempre activa: Toda acción importante queda registrada en BitacoraEventoResource. Si un usuario reporta un problema, revise la bitácora para ver qué ocurrió.
⚠️ No editar permisos en DB directamente: Siempre use el RoleResource de Filament Shield o el comando shield:generate. Modificar las tablas permissions o model_has_permissions directamente puede romper el sistema.
📄 Manuales en el topbar: Los PDFs de manuales se sirven desde public/docs/ y se enlazan desde un dropdown en el menú de usuario (esquina superior derecha). Configuración en AdminPanelProvider.php, hook USER_MENU_BEFORE.
✅ Resumen de lo que SÍ puede hacer el Super Admin:
  • Acceder a TODO el panel de administración (/admin) sin restricciones.
  • CRUD completo en los 42 recursos y acceso a las 19 páginas.
  • Gestionar usuarios y roles (asignar/revocar roles, crear/modificar/eliminar usuarios).
  • Ver y auditar todo el histórico de cambios (Bitácora de Eventos + Historial de Estados).
  • Aprobar, rechazar, condicionar y reabrir solicitudes de transporte, combustible y mantenimiento (actúa como Jefe de Transporte).
  • Realizar todas las operaciones del rol Operativo (tomar, validar, asignar recursos, asignación previa).
  • Ejecutar todos los endpoints de la API REST sin restricción de roles.
  • Exportar cualquier reporte en PDF, Excel o CSV.
  • Gestionar contratos (combustible y mantenimiento), lotes de combustible y liquidaciones.
  • Modificar parámetros del sistema, catálogos globales y catálogos de vehículos.
  • Gestionar incidencias, planificación de flota y asignaciones vehículo-motorista.
  • Ejecutar comandos Artisan: migraciones, seeders, shield:generate, etc.
  • Acceder a todos los reportes (10) sin filtros de datos.
  • Ver el dashboard con estadísticas completas de todo el sistema.
❌ Resumen de lo que NO puede hacer el Super Admin:
  • No puede crear solicitudes como solicitante desde el panel admin (eso es competencia de la app React externa).
  • No puede actuar como motorista en el flujo de viajes (iniciar/llegada/retorno/finalizar) desde el panel admin (solo vía API con rol motorista).
  • No puede acceder a las apps React de Solicitantes ni de Jefe (son sistemas separados).
  • No puede eliminar su propio rol super_admin desde la interfaz de Shield (Shield lo previene).
  • No debe modificar las tablas de permisos de Spatie directamente en la base de datos.
  • No puede usar la app móvil/self-service de motoristas (es exclusiva para el rol motorista).
  • No puede recibir notificaciones como solicitante de sus propias solicitudes (eso es del frontend React).
  • No puede cambiar el comportamiento de la app React externa (está en Vercel, fuera de este repositorio).
